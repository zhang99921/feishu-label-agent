现有扫码表单的后台接入

本轮代码保留现有“一张扫码流水表、入库出库转仓三张表单”的入口和字段。
新增入口是 worker.py，或 uv run finding-assistant-intake。
main.py 仍是原 HTTP 接口启动器，不会自动开启轮询。

已实现的处理范围
读取扫码流水 → 核对现有表结构 → 校验整单输入 → 单内箱号去重
→ 将任务及逐箱列表登记到 PostgreSQL → 保留输入变更事件。
正式箱表、行表、箱内明细、事务账的过账执行器尚未接入。
新增入口只接收任务，不会把接收成功当成入库/出库成功，也不向飞书写入处理结果。
原定时程序的幂等、状态校验、失败恢复规则仍需确认后衔接，不能以本轮代码替代。

离线检查现有导出文件
  uv sync --locked
  uv run python worker.py preview --export "D:\Downloads\仓库库存信息.base"
仅此命令不需要密钥或 PostgreSQL，也不会写入任何业务数据。

历史空状态记录
默认只接收明确标记“待处理”的记录，跳过已入账、已出账、已转仓及异常记录。
现有表单可能产生空处理状态。为避免接管时重新处理旧数据，空状态需显式启用，
并在接入真实执行器前确定历史待办的接管范围；不能直接把所有空状态视为新请求。
离线查看这些记录：
  uv run python worker.py preview --export "D:\Downloads\仓库库存信息.base" --include-blank-status

新HTTP流水的接收（2026-10-23）
新版入库、出库、转仓API由服务端将新建流水初始化为“待处理”；默认接收器可直接登记，
不必开启FEISHU_INCLUDE_BLANK_STATUS。接收器仍需按上文启动，HTTP进程不会自行开启轮询。
同一来源record_id重复读取只登记一次；任务和逐箱项目仍仅为后台接收数据，非库存事务账。
历史空状态流水保持原接管边界；旧成功请求的幂等重放不会为其补写待处理或创建新流水。

配置与 PostgreSQL
默认使用项目工作目录中的 .env；部署时也可直接注入同名环境变量，环境变量优先。
复制 .env.example 为 .env，填写 FEISHU_APP_ID、FEISHU_APP_SECRET、FEISHU_BASE_URL。
FEISHU_SCAN_TABLE_ID 明确指定扫码流水表ID，不使用当前浏览器正在打开的其他业务表。
Base 链接可解析底层标识；Wiki 链接在未填写 FEISHU_APP_TOKEN 时通过只读接口解析。
如应用无 Wiki 访问权限，可填写底层 FEISHU_APP_TOKEN，不要把节点 token 当 Base token。
在 .env 中填写 FINDING_ASSISTANT_DATABASE_URL 提供 PostgreSQL 连接字符串。
真实配置不提交 Git、不随代码交付；不将 Demo 应用凭据自动用于正式表。
可给 poll、db-init、status 命令追加 --env-file "绝对路径/.env" 来指定其他配置文件。
HTTP 启动入口 main.py 也支持 --env-file；不配置旧版实验白名单时，旧远端实验默认禁用。
先由有权限的维护人员显式运行迁移：
  uv run python worker.py db-init
它显式执行 finding_assistant schema 的四份迁移，包含任务、身份、写请求与审计共10张辅助表。
不会建立飞书新表，也不创建第二份库存主库。

接收一轮现有表单任务
  uv run python worker.py poll
持续后台轮询：
  uv run python worker.py poll --watch
查看已接收任务统计：
  uv run python worker.py status
查看异常任务和写入请求明细：
  uv run python worker.py inspect tasks --state BLOCKED
  uv run python worker.py inspect writes --state UNKNOWN
  uv run python worker.py inspect audit --outcome DENIED
这些命令只读PostgreSQL，不调用飞书、不修正状态；完整用法见“后台运维查询说明.txt”。
以上命令不会修改 Windows 定时任务，也不会停止或替换当前正在运行的旧程序。

运行前只读诊断（2026-10-22）
  .\.venv\Scripts\python.exe worker.py doctor
可追加 --env-file "配置文件的完整路径"。诊断读取配置、检查数据库连接及四份迁移的校验和，
不创建表、不修改记录、不调用飞书；结果仅显示固定错误码，不输出连接信息或密钥。
ready=true仅说明本次配置和数据库检查通过；feishu_checked=false表示没有验证飞书授权。
该检查不会启用扫码API或库存执行，HTTP_ONLY模式也不会因此变为可业务操作。

持续运行的故障行为
每轮接收前重新检查数据库及迁移。临时断线、来源超时和限流会在等待后重新读取。
连续失败从配置轮询间隔开始逐次加倍，默认30秒间隔时最多等待300秒；配置间隔本来
大于300秒时不缩短间隔。恢复后回到正常周期。日志只记故障来源和等待时间。
源分页读取不完整时不登记该轮记录；数据库中途断线时，已登记记录通过原来源键去重。
持续模式不会因临时断线直接退出；单轮poll仍以失败退出，不把失败当作接收成功。
迁移缺失、校验和冲突或数据库结构错误会停止，需要维护人员核实，不自动建表或改迁移。
停止持续轮询可使用Ctrl+C；程序关闭读取连接，不强制重发未知结果或改变库存状态。
持续接收支持SIGTERM/Windows SIGBREAK请求收尾：完成当前轮次后退出，等待退避时立即响应。
启动与轮询日志默认写入工作目录logs/intake.log，按大小轮转；不会创建服务器托管服务。
配置、日志容量和信号边界见“常驻运行与日志说明.txt”。

内部状态的含义
QUEUED：仅表示后台保存了结构上可接收的请求，未证明实物、箱号、行码或业务权限有效。
BLOCKED：输入缺项、格式错误或不在本轮支持的事件范围，不能执行库存写入。
RECONCILE：已接收的源记录内容被修改；保留原任务与逐箱列表，等待人工核实。
上述状态都不等同于飞书“已入账”“已出账”或“已转仓”。
缺失来源创建人会明确记录警示；有创建人也不能当成已经完成业务授权。

幂等与并发边界
请求身份由 Base token、扫码表 table_id、流水 record_id 组成。
同一流水同样内容反复轮询不会新建任务；同一流水改内容后不会静默覆盖。
同单重复箱号合并为一个逐箱任务；这不能代替跨请求重复出入库校验。
PostgreSQL 的唯一键和行锁只保证内部任务登记，不保证跨飞书 HTTP 写入的原子性。
执行器接入后仍需校验当前库存、授权、版本与失败恢复，再设计结果回写。
