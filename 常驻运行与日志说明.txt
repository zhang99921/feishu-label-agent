找货助手：常驻运行与日志说明
更新日期：2026-10-28（归档与审计默认保留策略更新）

一、日志配置

示例位于.env.example；未填写时使用以下默认值：
  FINDING_ASSISTANT_LOG_DIR=logs
  FINDING_ASSISTANT_LOG_MAX_BYTES=10485760
  FINDING_ASSISTANT_LOG_BACKUPS=5
  FINDING_ASSISTANT_LOG_RETENTION_DAYS=30
LOG_DIR相对进程工作目录解析；从E盘项目启动时即E:\Sourcing agent\logs。
也可填运行账号可写的绝对目录；显式留空则只输出到控制台，不修改现有密钥。
MAX_BYTES允许1MiB至100MiB，RETENTION_DAYS允许1至3650，默认30；非法配置拒绝启动相应日志。
BACKUPS仍接受1至10供旧配置兼容，不再按固定数量覆盖新归档。

HTTP后端main.py自身日志写入http.log；worker.py poll（含--watch）写入intake.log。
两个进程分别启动，main.py不自动启动poll，也不替换尚未交接的旧定时程序。
文件达到约10MiB或跨UTC日期时，压缩到archive/组件名/YYYY-MM-DD/组件-时间戳-UUID.log.gz。
默认保留当天及之前29个UTC日期；在首次/跨日写日志时清理更早的本组件严格命名归档。
停机/无日志期间不独立调度清理，下次写日志再检查；不是精确小时TTL。
单条限约16KiB，过长内容标注[truncated]。归档不按数量覆盖，30天容量取决于实际日志量。
旧.log.1等历史文件不自动迁移/删除；未知文件、其他组件、符号链接及非本格式文件不清理。
只逐文件删除本组件归档，不递归删除目录；不对办公电脑下载副本执行清理。
同一目录按一个HTTP进程、一个接收进程使用；多实例须各用独立LOG_DIR，
本模块不提供多进程共享文件的轮转协调。时间采用UTC，行首Z表示UTC。

二、记录范围

HTTP记录启动/停止、request_id、方法、路由模板、状态和耗时。
接口返回的X-Request-ID可用来定位日志；路由模板不展开箱号等路径参数。
接收进程记录启动/关闭、接收数量、故障来源、失败次数、退避时间和停止事件。
不记录URL查询参数、Cookie、Bearer、App Secret、请求体、连接串或原始异常正文。
程序自身日志附带异常时只记录异常类型，不保留堆栈正文。
本模块不对主动拼入消息的任意字符串自动脱敏；后续新增日志仍须沿用固定字段，
不能直接打印请求、响应或异常对象。

接管finding_assistant.http、finding_assistant.intake与finding_assistant.sync各自组件日志；
身份诊断finding_assistant.identity显式复用组件handler，HTTP优先，独立同步/接收进程使用各自通道。
Uvicorn进程启动信息仍在控制台，不将HTTP库的URL调试日志合并到运行文件。
数据库审计继续独立保留，文本日志不代替写请求、权限和会话审计。

三、日志故障和配置自检

目录无法创建或打开时，常驻入口返回固定配置/存储错误，不输出目录或异常原文。
运行中写日志或轮转失败时，控制台一次性提示RUNTIME_LOG_WRITE_FAILED；
原业务流程继续，不因日志故障重发请求或改变状态，维护人员需检查日志存储。
归档成功落盘后才截断活跃文件；归档/清理失败时尽量继续追加当前事件，相关操作退避60秒重试。
后续事件仍会尝试写入，故障期间未落盘的文本不会自动补回；需要监测固定告警及磁盘空间。

main.py --check-config仅检查参数，不创建日志目录、不探测目录写权限。
worker.py doctor、preview、status、inspect、db-init和db-maintain不因本模块创建日志文件；
db-maintain默认仅清理过期挑战和旧会话，不删除审计；审计期限另定后才显式传--audit-days。
日志及轮转文件不提交Git；交付不携带运行日志、真实.env、虚拟环境或测试材料。

四、停止持续接收

SIGTERM（以及Windows支持的SIGBREAK）设置停止标记，完成当前轮次后退出，
不再开始新一轮；等待正常间隔或故障退避时立即响应停止。
第一轮前收到信号时不读取来源、不登记任务；退出时关闭客户端并恢复信号处理器。
当前轮次已发出的网络/数据库调用仍受原有超时约束，停止标记不会取消已有调用。
Ctrl+C保留KeyboardInterrupt行为，命令返回130并走关闭客户端路径。
强制结束进程不代表任务完成；后续仍依赖原来源键去重，不将中断标成库存成功。

这里实现运行与停止机制，进程停止后不会自行拉起，也未配置系统服务或定时任务。
服务器托管方式和终止等待时间须结合目标操作系统与数据量配置，后续再部署。
实际库存入账、原程序切换仍等待负责人交接，不因本轮常驻能力而提前启用。
目标服务器日志、磁盘权限、停止收尾及24小时运行验收见“项目待办事项.txt”T003；
真实人员功能验收继续按T001、T002保留，本轮仅做开发侧检查。


分页同步与副本存储巡检（2026-10-23）
日常worker.py sync改为每页最多100条记录暂存至PostgreSQL，随后用服务端游标分批计算摘要和建立箱索引。
内存不再同时保留所有表记录或整张行表映射；单条记录大小、字段元数据和数据库自身资源仍影响实际占用。
所有配置内的表读完、字段前后复核一致、关联与数值校验通过后，才切换active_backup_id。
暂存阶段日常查询继续使用旧完整版本；失败不发布半成品，清理自己本轮未发布的暂存行并保留失败头。
中断遗留的本实现RUNNING暂存仅在下轮取得同一Base同步锁后回收；人工归档和已完成版本不在自动清理范围。
内容未变时删除本轮未发布暂存并刷新检查时间，不新增永久完整版本。
摘要算法升级首次生成一个新完整版本，后续相同内容复用；原版本继续保留。
仍是完整分页轮询，不是增量同步，也不是飞书跨表ACID快照。同步间隔仍为一轮结束后60秒。
日志增加耗时、记录数、记录页数和最大页条数，不写入业务原文、令牌或连接串。

运维命令（在项目根目录执行；只读SQL，不访问飞书）：
  uv run python worker.py backup-storage
  uv run python worker.py backup-prune-preview --keep-days 30 --keep-latest 2
第二条仅演示预览参数，未将30天或2个版本设为正式保留策略。参数必须显式提供。
preview返回候选数量和分页版本清单，deletion_executed始终为false；本次未提供历史版本删除入口。
预览限定当前Base、相同同步表范围的成功日常副本，保留活动查询版本、权限依据引用、最近N个版本、显式保护版本及人工归档。
其他Base/范围、失败或进行中版本不作为预览候选；保护标记为metadata的protected/pinned/retain=true或retention=keep。
backup-storage区分当前Base记录逻辑体积与全部Base共用表/索引的物理体积；统计有10秒超时，数据量过大应另行安排巡检。
暂存写入与删除仍产生数据库I/O和可重用空闲页；删除不会立即缩小PostgreSQL磁盘文件，需要数据库常规autovacuum维护。

本次复用现有21张后台表与9份迁移，无需新增建表或修改已安装迁移。
正式源表保持只读；普通账号SQL行列范围开关保持关闭，原库存执行和位置分配开关不变。
